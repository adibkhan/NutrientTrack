# NutrientTrack

Local-first nutrition diary PWA (React 18, TypeScript, Vite). All user data lives in the visitor's browser (IndexedDB `nutrienttrack-local`), which stays the primary copy. Signing in turns on optional cloud backup and sync through Supabase (`public.sync_records`, see `supabase/`). The Cloud Run container only serves static files.

## Gates

Run all three before calling work done. CI runs them on every PR and blocks deploys on failure.

- `npm run typecheck` (`tsc -b --noEmit`)
- `npm test` (Vitest + jsdom)
- `npm run build`

## Deploy

Merging to `main` deploys via `.github/workflows/deploy.yml`, which uses Cloud Build to deploy to the Cloud Run service `nutrienttrack` (project `prisential-prod`, us-central1), then smoke-tests the site. It is served at https://nutrienttrack.com. The health check is `/health`; Cloud Run reserves paths ending in `z`, such as `/healthz`. Users' data is tied to the exact origin, so share only `nutrienttrack.com`.

## Data invariants

The browser holds the primary copy, and most users have no server copy at all because sync is opt-in. A change that breaks stored data loses it for good. These rules outrank feature work. Breaking one is a blocking defect, and a rule without an enforcing test is itself a finding.

1. **Fields are additive.** New fields are optional. A missing value means "not recorded", never zero. Never rename, remove, or repurpose a stored field.
   - Enforced by: `src/lib/db.test.ts` (the v1 fixture round-trips with its unknown fields intact), `src/lib/backup.fixtures.test.ts` (v1 and v2 fixtures, unknown fields on entries, settings and program) and `src/lib/backup.nutrients.test.ts` (every optional field accepted when absent).
2. **Edits preserve unknown fields.** Saves start from the stored record (`{ ...existing, ...fromForm }`). They clear only the optional fields the form owns (`ENTRY_FORM_OPTIONAL_KEYS` in `src/App.tsx`). A record written by a newer build must survive an edit by an older one.
   - Enforced by: `src/App.durability.test.tsx`, plus the unknown-field cases in `src/App.nutrients.test.tsx`, `src/App.planned.test.tsx`, `src/App.program.test.tsx`, `src/App.preferences.test.tsx`, `src/App.favorites.test.tsx`, `src/App.bodyfat.test.tsx` and `src/App.measurements.test.tsx`.
3. **Schema changes are numbered migrations.** Append a step to `MIGRATIONS` in `src/lib/db.ts`; `DB_VERSION` follows its length. Never edit or remove a shipped step. Bump only for new stores or indexes, or when data must be rewritten; a new optional field needs no bump.
   - Enforced by: `src/lib/db.test.ts`, which opens a database created by the original v1 code, and `src/lib/db.local-stores.test.ts`, which upgrades a version 2 database to the current version.
4. **Old backups always restore.** A backup format change bumps `BACKUP_VERSION` and appends a `BACKUP_MIGRATIONS` step in `src/lib/backup.ts`. A backup from a newer build is refused with a clear message, never corrupted.
   - Enforced by: `src/lib/backup.fixtures.test.ts` and `src/lib/backup.v2.test.ts` (a version 1 file is upgraded with empty water and measurement logs; the next version is refused as newer).
5. **Fixtures are frozen.** Files in `src/lib/__fixtures__/` record real formats that users hold. Never edit one; add a new file for each new version and keep testing every old one.
   - Enforced by: `src/lib/invariants.test.ts`, which pins each fixture's content fingerprint.
6. **Imports and clears are atomic.** `importBackup` and `clearAllData` run in a single transaction.
   - Enforced by: `src/lib/db.test.ts` (the synchronous and mid-transaction failure tests for import, clear and batch save) and `src/lib/db.local-stores.test.ts` (water and measurements are part of the same import and clear).
7. **The catalog is versioned by file name.** The catalog is cached by URL (`force-cache`, then the service worker). A content change ships as a new file, e.g. `usda-common-v2.json`, and is added to `APP_SHELL` in `public/sw.js`. Catalog IDs are never reused. Diary entries store nutrition snapshots, so catalog changes never rewrite history.
   - Enforced by: `src/lib/invariants.test.ts`, which pins the catalog content to its file name and checks the service worker precaches that file.
8. **Multiple tabs are expected.** `db.ts` handles `blocked` and `versionchange`, so an old tab closes its connection instead of blocking an upgrade, and the UI asks the user to reload.
   - Enforced by: the database events tests in `src/lib/db.test.ts` and the event message tests in `src/App.durability.test.tsx`.

## Cloud sync

- **Schema:** changes go in a new file under `supabase/migrations/` (never edit an applied one). Apply with `npm run db:migrate` and test with `npm run db:test`; both need `DATABASE_URL`, the Supabase session pooler (IPv4) URL. Never commit it.
- **Keys:** the app uses only the publishable key in `src/lib/cloud.ts`, which is public by design. Never put a secret or service-role key in the app, the repo, or CI.
- **Sync rules** (note that clearing local data while signed in signs the device out first, so the next sync can't pull the data back):
  - Last write wins on `client_updated_at`, enforced by the database trigger.
  - Deletes are markers; devices never hard-delete rows.
  - Restoring a backup and "Clear local data" never delete anything in the cloud.
- **Failure rules** (each has a test in `src/lib/sync.test.ts`, `src/lib/outbox.test.ts`, `src/lib/cloud.test.ts` or `src/App.cloud.test.tsx`):
  - A record the server rejects is set aside and reported, never retried forever; one bad row must not block the rest.
  - Pull always runs, even when push failed.
  - Cloud records are validated before they are stored locally (`isValidSyncRecord`).
  - Restoring a backup resets the pull cursor; deletes are queued only once a device has synced (`everSynced`).
  - "Clear local data" decides from the stored session (`hasStoredSession`), and sign-out works offline.
- **Database scripts:** `npm run db:migrate` and `db:test` verify the server certificate against `supabase/prod-ca-2021.crt` (Supabase's public root CA, valid to 2031). Never turn verification off; point `DATABASE_CA` at another CA file if the host changes.
- **Local-only stores:** `water` and `measurements` (DB version 3, backup version 2) and `symptoms` (heartburn flares for reflux watch; DB version 4, backup version 3) are saved on the device and in backups but are not synced, because `public.sync_records.store` is restricted to `entries`, `foods`, `weights` and `settings`. To sync them, add a new file under `supabase/migrations/` that widens that check, apply it, then add the stores to `SYNCED_STORES` in `src/lib/db.ts` and to `isValidSyncRecord`. Do both together or not at all.
- **Loading:** the Supabase library is loaded only when someone asks for a sign-in link or already has a session (`src/lib/cloud.ts`, gated by `mightBeSignedIn`). People who never sign in never download it, and the offline app must not depend on it. The same rule covers the ZXing barcode decoder (`src/lib/scanner.ts`): it is imported only when someone opens the scanner, the browser's own BarcodeDetector is used first where it exists, and the Open Food Facts lookup (`src/lib/barcode.ts`, third party) runs only after `preferences.barcodeLookup` is switched on. The scanner itself no longer waits for that opt-in: a scanned or typed code is looked up first in the self-hosted branded index (see Branded foods), which sends nothing to anyone else.

## Static food pages

`npm run build` ends with `scripts/build-food-pages.mjs`, which writes one plain HTML page per catalog food under `dist/foods/<category>/<food>/`, a page per category, `/foods/` and `/sitemap.xml`. They share `/foods/foods.css`, load no app JavaScript and make no third-party requests. Each links into the app with `/?log=<catalog id>`, which opens the logger on that food. The service worker leaves `/foods/`, `/recipe-calories/`, `/sitemap.xml` and `/robots.txt` to the network so a food page is never cached as the app shell (`src/sw.test.ts`). Tested in `src/foodPages.test.ts`.

The catalog is built with `node scripts/build-usda-catalog.mjs --zip <SR Legacy CSV zip>` (source: `FoodData_Central_sr_legacy_food_csv_2018-04.zip`, sha256 `b80817294b8850530aaedf2e515c02593b1824f763a0ff356e5c2081643e6fd0`). Version 2 adds USDA household measures as `portions`; with them removed it is byte-for-byte the version 1 data.

## Branded foods (US packaged foods, barcode lookup)

`public/data/branded-v1/` holds a self-hosted index of USDA FoodData Central Branded Foods (CSV release 2026-10-29, zip `branded.zip`, sha256 `17f1e52ea91854d8c6c266487597bf1dd6ce63441bfe27c9e61f64e2768440c7`): 428,605 products, one per GTIN. It is built with `node scripts/build-usda-branded.mjs --dir <extracted CSV dir>` (streams the CSVs, about 110 s, deterministic: two builds are byte-identical; no dependencies; `--max-old-space-size=5000` on small machines; `--dropped file.jsonl` lists every dropped GTIN with its reason) and COMMITTED: the Docker build just serves it (`scripts/*` is not in the image on purpose). Layout (manifest `version` 2, directory still `branded-v1` because it has never shipped): `manifest.json` (about 175 kB, fixed name, pinned by `src/lib/invariants.test.ts`) plus two PACK files `branded-pNN-<sha256 first 12 hex>.bin` (each at most 25 MB, about 34.1 MB in all). A pack is individually gzipped shards concatenated; the manifest gives `[pack, offset, length]` per shard, and `src/catalog/branded.ts` reads one with a `Range` request and gunzips it (`DecompressionStream`, with a pure inflate fallback that checks the CRC-32 and length; a native data error is final). Five shard kinds: `detail` (GTIN-ordered JSON rows with every nutrient), `summaries` (one TSV line per product, stored once, in blocks of 500 rows in GTIN order), `pop` (one popularity level byte per product, one 90 kB shard, fetched once), `posts` (postings for EVERY token as delta-varint ordinals, consecutive token ranges of about 32 kB, a token with long postings has a shard of its own so one Range reads it) and `heads` (the 200 best products of each common word and 100 of each very common word pair). Matching is EXACT: a query reads the postings of its words (all of them when the rarest has at most 3,000 products, else the two rarest) and intersects them in memory. A small match set (24 or fewer) is read whole from its summary blocks; a big one is ranked with the head of its pair or rarest common word, then the popularity levels, and only the blocks of its best candidates are read. A cold two-word query is about 3 to 6 requests and 50 to 170 kB; a single common word is one request of about 30 kB. The tokeniser is shared by the build (`scripts/lib/branded-text.mjs`) and the client and a parity test keeps them equal (digits and percents kept, m&m / h-e-b / a&w joined, "la croix" = lacroix, accents folded, typo repair against 5,000 brand words). Build rules worth knowing: the newest record of a GTIN wins, an older live record rescues it when the newest fails a check, and a GTIN whose newest record is discontinued is kept from its newest live record (else its newest discontinued one) and flagged `discontinued`; lost check digits are completed and merged, UPC-E is merged into its UPC-A twin, store-local codes (UPC number system 2 or 4, EAN 20-29) are searchable but never scannable; serving units are cleaned (MG is grams, a household amount that disagrees with the size wins when plausible); liquids stay per 100 ml with `unit: 'ml'`; zero-kcal oils and sprays are flagged `labelRounded`. A content change ships as `branded-v2/`, never an edit of v1 once deployed (invariant 7); the packs are not in the service worker's precache and must stay out of it, and the service worker must let `Range` requests for `/data/branded-v1/` go straight to the network (the UI phase wires that; `python -m http.server` ignores Range, so use `node scripts/serve-static-range.mjs <dir> [port] [--no-range]` to try it locally). nginx serves `/data/branded-v1/*.bin` with `gzip off`, an immutable cache and `etag on; if_modified_since exact;`; the Dockerfile gives every file in `dist/data/branded-v1/` a content-derived mtime after the build so the ETag (mtime + size) is identical on every instance. The library is not imported by the app yet; when it is, import it dynamically with a caught failure path (never `React.lazy`).

How the app uses it (`src/lib/brandedApp.ts` is the only door; `branded.ts` is imported statically ON PURPOSE, about 12 kB gzip: a lazy chunk is not in the service worker's precache and is wiped by a `CACHE_NAME` bump, so brand search would fail offline right after an update, and `src/noLazy.test.ts` forbids lazy loading anyway): the Log food sheet shows a "Brands" group under the generic USDA results from 3 characters (`src/lib/brandedUi.ts` holds the debounce, row limits, ranking and barcode-digit rules); a barcode scan, or 12/13/14 digits (8 only when a valid EAN-8 or UPC-E check digit) typed in the search box, goes to `lookupBarcode`, opens its product ONCE and clears the box, so Back lands on an empty search; `/?log=usda-branded-<gtin>` opens the logger on that product. Branded foods get no static pages. Every failure is quiet (a one-line note, generic results keep working): offline says "Brand search needs a connection", a timeout says "Brand search is slow right now. Try again" with a Retry button, and a server that ignores Range says "isn't available on this connection" (remembered for 24 h per manifest fingerprint in localStorage). The Brands group is rendered once and moved with CSS `order`, keeps its previous rows (dimmed) while a newer search loads, and decides above/below the generic results once per settled query. Search reads the last word typed as a prefix union and never drops an earlier word; entries logged in ml carry `unit: 'ml'` (CSV column "Amount unit"). The packs are fetched with the default cache mode, and nginx sends `no-store` for a 404 under `/data/branded-v1/` (never `immutable always`), because a cached 404 for a pack would break brand search for a year.

Stored entries (invariants 1 and 4): a branded entry keeps `catalogId: 'usda-branded-<gtin>'`, its grams, its name with the brand in it, and the label nutrients it had, but NO `catalogSource`. Builds from before branded foods validate `catalogSource` against `'USDA SR Legacy' | 'USDA Foundation'` and would refuse the whole backup (and the sync record) holding any other value, so `storedCatalogSource` (`src/lib/brandedUi.ts`) drops `'USDA Branded'` at every write. The type and the validator in `src/lib/backup.ts` do accept `'USDA Branded'` on read. Tested in `src/lib/backup.branded.test.ts`.

Offline: the page keeps every fetched shard (gzipped bytes) in the Cache API cache `nutrienttrack-branded-v1` (`src/lib/brandedCache.ts`, synthetic URLs `/__branded/<fingerprint>/<pack>/<offset>-<length>`, where the fingerprint hashes the manifest version and pack names and sizes, so a rebuilt index never reads old shards and the old ones are deleted on first use, at most 300 shards, least recently used out). `public/sw.js` leaves every Range request and every pack to the network (never cached: a 206 stored as a file would corrupt reads), serves `manifest.json` network first with the copy in that same cache as fallback, and its activate cleanup keeps every `nutrienttrack-branded-*` cache across a `CACHE_NAME` bump (`src/sw.test.ts`).

## Pip

Pip is drawn once, in `src/components/Mascot.tsx`, under one light rig (key light upper left, rim right, occlusion at the ground; colours only from the `--pip-*` tokens). `scripts/brand/pip.mjs` is generated from that drawing by `scripts/brand/export-pip.mjs` and feeds the app icons and share image (`scripts/brand/render.mjs`); never edit it by hand. `scripts/brand/contact-sheet.mjs` renders every mood, reaction and stage at three sizes in both themes; run it after any change to Pip and look at the result. Both scripts build `scripts/brand/sheet` with `vite build --config scripts/brand/vite.sheet.config.ts` first and need Playwright, which is not a project dependency.

## Recipe calorie calculator

`/recipe-calories/` is a second Vite page (`recipe-calories/index.html`, `src/recipe/`) that shares the catalog, the describe-to-log matcher (`src/lib/describe.ts`) and the stylesheet. It stores nothing: the recipe lives in the page address (`#i=<lines>&s=<servings>`), and the copyable label (`src/lib/recipe.ts`) is inline-styled HTML with one credit link. The service worker leaves it to the network like the food pages, nginx serves it with `no-cache`, and it is listed in the sitemap.

## Conventions

- Keep diffs small, and add a regression test that fails before the fix.
- UI changes need browser proof at 320px width in both light and dark, with an empty database and a populated one. Theme is a stored preference (`settings.preferences.theme`); colours come only from the tokens at the top of `src/styles.css`, never hard-coded.
- Design tokens live at the top of `src/styles.css` (the "Standard Compact" system: white surfaces, `#2E6FE8` accent, 10px cards / 8px controls, 44px rows). IBM Plex Sans is self-hosted from `public/fonts/` and precached by the service worker; never load fonts or other assets from a CDN, since the app must work offline and makes no third-party requests.
- `.claude/panel-log.md` records review panels. Append to it; don't rewrite it.
